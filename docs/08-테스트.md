# 08. 테스트

## 1. 테스트 전략

| 원칙 | 내용 |
|---|---|
| 실서버 불가침 | 테스트 중 **실제 Supabase 서버에 요청하지 않음**. 브라우저에서 `window.fetch`를 가짜 서버로 바꿔 끼워 응답을 만들고 요청을 기록 |
| 실데이터 보호 | 테스트 전에 `localStorage` 전체를 백업, 끝나면 그대로 복원 (실사용 중인 기기 데이터 보존) |
| 시나리오 단위 | 함수 단위 테스트 프레임워크 없이, 사용자 시나리오(가입 → 인증번호 → 로그인 → 동기화 …)를 처음부터 끝까지 실행하고 **결과 상태 + 요청 기록**을 확인 |
| 보안 시나리오 포함 | 정상 흐름뿐 아니라 공격 시나리오(공격자 토큰 링크, 악성 서버 데이터)를 테스트 케이스로 |
| 모바일 기준 화면 확인 | 375×812 뷰포트에서 스크린샷으로 레이아웃 확인 |
| 정적 검사 | `index.html`에서 `<script>` 본문을 추출해 `node --check`로 문법 검사 (중첩 IIFE가 있어 첫 블록을 정확히 추출) |
| 안전한 수정 | 코드 수정은 "정확히 N번 일치해야 바꾸는" 패치 스크립트(Python)로 → 의도치 않은 위치 변경 방지 |

## 2. 테스트 환경

| 항목 | 내용 |
|---|---|
| 개발 PC | Windows 11 |
| 실행 | 로컬에서 `index.html` 구동 (브라우저 미리보기) |
| 뷰포트 | 모바일 375×812 (iPhone 크기) |
| 서버 | `fetch` 모킹 (Supabase Auth · REST 응답을 가짜로 생성) |
| 정적 검사 | Node.js `node --check` |
| 서비스워커 | Node.js `vm`으로 `sw.js`를 수정 없이 불러와 가짜 `self`·`caches`·`fetch`로 fetch 처리 규칙 시험 ([`tests/sw-cache-policy.test.js`](../tests/sw-cache-policy.test.js)) — 미리보기 브라우저에서는 서비스워커 등록이 막혀 있어 이 방법 사용 |
| 실기기 | iPhone 홈 화면 앱 (배포 후 사용하며 확인) |

### 모킹 구조 (설명용 예시)

```js
// 테스트 전: 실데이터 백업
const saved = JSON.stringify(Object.assign({}, localStorage));
// 가짜 서버: 요청을 기록하고 경로별로 응답
const calls = [];
const db = { events: [], categories: [], prefs: [] };
window.fetch = async (url, opt = {}) => {
  calls.push({ url: String(url), method: opt.method || "GET", body: opt.body });
  // /auth/v1/token, /auth/v1/verify, /rest/v1/events ... 경로별 가짜 응답
  // 오프라인 시나리오: throw new TypeError("Failed to fetch")
};
// 검증 예: 공격자 링크 시나리오에서 /rest/v1/ 요청 수 === 0
// 테스트 후: localStorage.clear(); 백업 복원
```

## 3. 테스트 케이스

**결과 표기**: `통과` = 모킹 시나리오 테스트로 통과 확인 · `확인` = 개발 중 화면에서 동작 확인(상세 기록 미보존)

> 2026-11-04 재검증: 처음 문서화할 때 실행 기록이 없던 11건(TC-10~14, 24, 26, 34~36, 38)을 v43 코드로 다시 실행해 모두 통과.

### 3.1 동기화 · 인증 (모킹 시나리오 테스트)

| ID | 시나리오 | 절차 | 기대 결과 | 결과 |
|---|---|---|---|---|
| TC-15 | 로그인 실패 메시지 | 가짜 서버가 `invalid_credentials` 반환 → 로그인 | "이메일 또는 비밀번호가 틀려요", 로그인 안 됨 | 통과 |
| TC-16 | 첫 로그인 합치기 | 서버: 이름을 바꾼 기본 카테고리 + 일정 / 기기: 기본 카테고리 + 로컬 전용 일정 → 첫 로그인 | 서버의 수정된 카테고리가 유지되고, 로컬 전용 일정만 업로드 | 통과 (이 테스트에서 버그 발견 → 수정 후 통과, §5 B-01) |
| TC-17 | 다른 기기 변경 수신 | 가짜 서버에 다른 기기가 추가 · 수정 · 삭제(tombstone)한 행 → `sync()` | 기기에 추가 · 수정 반영, 삭제된 일정 제거 | 통과 |
| TC-18 | 악성 서버 데이터 정제 | 서버 행에 형식 위반 `type`, 잘못된 id · 색(속성 탈출 문자열) · 날짜, id 불일치 `data` | 위반 항목은 반영 안 됨/정제됨, 화면에 스크립트 실행 없음 | 통과 |
| TC-19 | 오프라인 큐 → 업로드 | `fetch`가 `TypeError` → 일정 추가 · 수정 → 연결 복구 → `online` | 오프라인 중 `오프라인` · "올릴 것 N개", 복구 후 업로드되고 `방금` | 통과 |
| TC-20 | 충돌 시 최신 수정 승리 | 같은 일정을 서버(더 나중 시각)와 기기에서 수정 | 더 나중 `updated_at` 쪽이 남음 (양방향 확인) | 통과 |
| TC-21 | 삭제 → tombstone | 로그인 상태에서 일정 삭제 → `sync()` | 업로드 본문 `deleted: true`, `data: {}` | 통과 |
| TC-22 | 비밀번호 미저장 | 로그인 · 비밀번호 변경 후 `localStorage` 전체 검사 | 어떤 키에도 비밀번호 문자열 없음 (토큰만) | 통과 |
| TC-23 | 오래 만료된 액세스 토큰 | `expires_at`을 30일 전으로 설정 → 앱 실행 | refresh 토큰으로 갱신, 로그인 유지 · 동기화 성공 | 통과 |
| TC-25 | **공격자 토큰 링크 (로그인 CSRF)** | 기기에 일정이 있는 상태로 `#access_token=<공격자 토큰>&type=...` 주소로 열기 | 로그인 상태 아님, `/rest/v1/` **데이터 요청 0건**, 주소에서 해시 제거 | 통과 |
| TC-27 | 다른 계정 합치기 확인 | owner = A인 기기에서 B로 로그인 → 확인 / 취소 각각 | 확인: B로 로그인 · 일정 업로드 / 취소: `logout?scope=local` 호출, 로그인 안 됨, 업로드 0건, "로그인 취소됨" | 통과 |
| TC-28 | OTP 틀림 | 가짜 서버 `otp_expired` → 6자리 입력 | 칸 빨강(`.bad`), "인증번호가 틀렸거나 만료됐어요", 칸 비우고 다시 입력 가능 | 통과 |
| TC-29 | OTP 자릿수 부족 | 5자리 입력 후 `확인` | 요청 없이 "메일로 온 숫자 6자리를 입력하세요" | 통과 |
| TC-30 | OTP 다시 보내기 | `다시 보내기` | `resend`(가입) / `recover`(재설정) 호출, "다시 보냈어요", 칸 비움, 5:00 타이머 재시작 | 통과 |
| TC-31 | OTP 자동 확인 | 6번째 숫자 입력 (또는 6자리 붙여넣기) | 버튼 없이 `verify` 1회 호출 | 통과 |
| TC-32 | OTP 가입 성공 | 가입 → 올바른 6자리 | `verify(type=email)` → 로그인 → 동기화 실행 | 통과 |
| TC-33 | 비밀번호 찾기 → 자동 로그인 | `비밀번호 찾기` → 6자리 → 새 비밀번호 ×2 → `변경` | `verify(type=recovery)` → `PUT /user` → 로그인 상태 + "비밀번호 변경됨" | 통과 |

### 3.2 동기화 · 인증 (2026-11-04 재검증)

| ID | 시나리오 | 절차 | 기대 결과 | 결과 |
|---|---|---|---|---|
| TC-24 | refresh 실패 | 만료 토큰 + 미업로드 1건 상태에서 refresh 요청에 400 → 같은 계정으로 다시 로그인 | `auth` 삭제 · `sync` 유지, 메뉴 `다시 로그인`(빨강), 재로그인 시 미업로드분 이어서 업로드 | 통과 — 합치기 질문 없이 재로그인, 남아 있던 1건 업로드 후 `방금` |
| TC-26 | 재설정 링크 (호환 경로) | `#access_token&type=recovery`로 열기 → 새 비밀번호 | 토큰 주인 이메일 표시, 비밀번호 변경 후 임시 세션 폐기, **자동 로그인 안 함** | 통과 — 요청은 `GET /user` → `PUT /user` → `logout?scope=local` 3건뿐, `/rest/v1/` 0건, 이메일 채운 로그인 화면 |
| TC-34 | 비밀번호 변경 · 현재 비밀번호 틀림 | 틀린 현재 비밀번호로 `변경` | "현재 비밀번호가 틀려요", `PUT /user` 호출 없음 | 통과 — 로그인 상태 유지 |
| TC-35 | 이미 가입된 이메일 | 가입 응답 `identities: []` | "이미 가입된 이메일 · 로그인을 누르세요", 인증번호 화면으로 안 감 | 통과 |
| TC-36 | 로그아웃 | 로그인 상태에서 `로그아웃` → 확인 | `logout?scope=local`, `auth`·`sync` 삭제, `owner`·일정 유지 | 통과 — 이때 `sync` 키가 빈 초기값으로 다시 저장되는 현상 발견 → B-11, v44에서 수정 (TC-40) |
| TC-38 | 비로그인 시 서버 요청 없음 | 로그인하지 않고 일정 추가 · 수정 · 카테고리 이름 변경 · 숨김 켜고 끄기 | Supabase 요청 0건 (공휴일 API 제외) | 통과 — 전체 요청 기록에 Supabase 0건 |
